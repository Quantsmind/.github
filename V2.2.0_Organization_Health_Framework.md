## 1. Framework Overview

This organization health framework provides measurable, evidence-based indicators for QuantsMind GitHub organization health. It track repository-level and organization-level metrics without using stars, forks, or artificial engagement as primary success measures.

**Key Principle**: Evidence-based indicators only. No star counts, fork counts, or artificial engagement metrics. All indicators are derived from repository metadata, configuration, and content quality.

**Scope**: All 46 repositories (4 public + 42 private) under the QuantsMind organization.

**Review Cycle**: Quarterly (every 3 months) with annual summary.

---

## 2. Repository Health Indicators

Each repository is assessed across 8 health dimensions. Each dimension is scored as:

- **✅ Fully met** — All criteria satisfied
- **⚠️ Partially met** — Some criteria satisfied, some missing
- **❌ Not met** — No criteria satisfied or repo not inspected

### Indicator 1: Description Completeness

| Criterion | ✅ Fully | ⚠️ Partially | ❌ Not |
|-----------|----------|--------------|--------|
| Non-null description present | Description is set and non-empty | Description is `null` or placeholder | — |
| Description accurately reflects project purpose | Description clearly states what the project does | Description is generic or misaligned | — |
| Description length appropriate | 50–500 characters | Description too short (<20) or too long (>500) | — |

### Indicator 2: Topic Coverage

| Criterion | ✅ Fully | ⚠️ Partially | ❌ Not |
|-----------|----------|--------------|--------|
| Topics present | 3–10 GitHub topics configured | 0–2 topics or >10 topics | — |
| Topics are relevant | All topics relevant to project capabilities | Some topics irrelevant or generic | — |
| Topics are standardized | Lowercase, hyphenated as needed | Mixed case, spaced, or non-standard | — |

### Indicator 3: README & Documentation Quality

| Criterion | ✅ Fully | ⚠️ Partially | ❌ Not |
|-----------|----------|--------------|--------|
| `README.md` present | Yes, at repository root | No `README.md` or in non-standard location | — |
| Getting-started guide | Yes, clear installation/setup instructions | Partial or unclear guidance | — |
| Documentation link | Yes, `docs/` directory or external URL | No documented location | — |

### Indicator 4: License Presence

| Criterion | ✅ Fully | ⚠️ Partially | ❌ Not |
|-----------|----------|--------------|--------|
| `LICENSE` file present | Yes, at repository root with SPDX identifier | `LICENSE` file without SPDX identifier | — |
| License is OSI-approved | Yes, recognized open source license | Proprietary, "all rights reserved," or no license | — |
| License declared in README | Yes, badge or text reference | No declaration | — |

### Indicator 5: Contribution Guidance

| Criterion | ✅ Fully | ⚠️ Partially | ❌ Not |
|-----------|----------|--------------|--------|
| `CONTRIBUTING.md` present | Yes, at repository root with build/test/deploy instructions | Partial or unclear | — |
| Code of conduct | Yes, `CODE_OF_CONDUCT.md` present | No code of conduct or generic placeholder | — |
| Contribution workflow | Yes, PR process described | Partial or missing | — |

### Indicator 6: Open Issue Maintenance

| Criterion | ✅ Fully | ⚠️ Partially | ❌ Not |
|-----------|----------|--------------|--------|
| Open issues triaged | All open issues have appropriate labels (bug, question, etc.) | Some open issues without labels | — |
| Issue age distribution | No issues older than 6 months without activity | Issues older than 6 months with no resolution | — |
| Response time | Issues responded to within 30 days | Issues take longer than 30 days for first response | — |

### Indicator 7: Release Documentation

| Criterion | ✅ Fully | ⚠️ Partially | ❌ Not |
|-----------|----------|--------------|--------|
| Release tags present | Yes, at least one release tag | No release tags or all archived | — |
| Changelog | Yes, `CHANGELOG.md` covers released versions | Partial or missing `CHANGELOG.md` | — |
| Release notes | Yes, each release has descriptive notes | No descriptive release notes | — |

### Indicator 8: Security Policy

| Criterion | ✅ Fully | ⚠️ Partially | ❌ Not |
|-----------|----------|--------------|--------|
| `.github/SECURITY.md` present | Yes, with reporting guidelines | No security policy file | — |
| Security policy is actionable | Yes, includes contact method and triage process | Present but vague or incomplete | — |
| Security policy is up to date | Yes, updated within last 12 months | Not updated in over 12 months | — |

## 4. Health Score Calculation

**Per-Repository Health Score**: Percentage of 8 indicators fully met (0–100%).

| Score Range | Classification |
|-------------|----------------|
| 80–100% | ✅ Healthy |
| 50–79% | ⚠️ Needs Attention |
| 0–49% | ❌ Critical |

**Organization Health Score**: Average of all per-repository health scores.

**Trend Tracking**: Quarterly comparison against baseline. Improvement or degradation > 10 percentage points triggers maintainer review.

## 5. Evidence Collection Methods

| Indicator | Collection Method | Evidence Stored |
|-----------|-------------------|-----------------|
| Description completeness | GitHub API: `description` field | Metadata log |
| Topic coverage | GitHub API: `repositoryTopics` names | Topic inventory |
| README quality | Repo inspection: `README.md` existence and content | README audit report |
| License presence | Filesystem: `LICENSE`, `LICENSE.md` at root; SPDX identifier check | License compliance log |
| Contribution guidance | File existence: `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` | Contribution audit |
| Issue maintenance | GitHub API: issue labels, createdAt timestamps | Issue triage report |
| Release documentation | GitHub API: release tags, `CHANGELOG.md` existence | Release audit |
| Security policy | File existence: `.github/SECURITY.md` content review | Security policy log |

**Evidence Storage**: All evidence stored in `.github/` repository, `health/` directory, quarterly subdirectories.

## 6. Privacy & Boundary Enforcement

| Category | Indicators Allowed | Indicators Prohibited |
|----------|--------------------|-----------------------|
| **Public repos** | All 8 indicators fully applicable | None prohibited |
| **Private repos** | Description completeness, topic presence (if set), license presence (if set), security policy (if publicly disclosed) | ❌ Issue maintenance metrics (no access) ❌ Release documentation metrics (no access) ❌ Contribution guidance (partial; only if publicly visible) |
| **Organization-level** | Overall counts, trend percentages | ❌ Individual private repo details ❌ Private repository inventory in summary reports ❌ Confidential metrics |

**Boundary Rule**: Any indicator that requires access beyond publicly visible metadata is marked "TBC" (To Be Confirmed) and excluded from public reporting. Only indicators derivable from GitHub API data without elevated permissions are reported in public documentation.

## 7. Quarterly Review Procedure

### 6-Month Periodic Review (V2.2.0 WP6 carry-forward)

| Step | Owner | Output |
|------|-------|--------|
| 1. Inventory all 46 repos | Org maintainer | Repo list with current metadata |
| 2. Assess 8 indicators per repo | Maintainers (assigned repos) | Per-repository health score |
| 3. Compile organization metrics | Org maintainer | Dashboard with trends |
| 4. Identify regressions (>10pp change) | Org maintainer team | Action items |
| 5. Document exceptions and rationale | Org maintainer | Governance log entries |
| 6. Plan next quarter's focus | Org maintainers | Priority list for next quarter |

**Duration**: 2–3 days spread over 6-week period  
**Commitment**: 2 hours per maintainer per quarter

## 8. Annual Governance Review

### Yearly Review (end of each calendar year)

| Component | Description |
|-----------|-------------|
| **Health Score Trend** | Compare current year's average health score against prior year |
| **Policy Effectiveness** | Review whether lifecycle policy (WP1) and promotion policy (WP2) are achieving goals |
| **Metric Refinement** | Adjust indicator criteria based on observed data and organizational growth |
| **New Indicator Consideration** | Evaluate if new evidence-based indicators should be added |
| **Privacy Boundary Review** | Confirm no private information leaks into public health reports |
| **Next Year's Schedule** | Confirm quarterly review dates and maintainer assignments |

**Annual Review Output**:
- Updated health framework document (current year version)
- Revised metric definitions if needed
- Maintainer assignment calendar for next year
- Governance log archival for the year
- V2.x+1 campaign planning input

## 10. No Artificial Engagement Measures

**Prohibited metrics (explicitly excluded)**:

| Metric | Reason for Exclusion |
|--------|---------------------|
| Star count | Artificially inflatable; not indicative of project health |
| Fork count | Derivative measure; not under organizational control |
| Watch count | Passive engagement; not meaningful health indicator |
| Open PR count per developer | Individual workload metric, not organizational health |
| Issue velocity | Can be gamed; requires per-developer tracking |
| Contributor count | Can be inflated; not all contributors are active maintainers |

**Allowed alternatives**:
- Issue label distribution (triage status, scope categories)
- Repository metadata completeness (descriptions, topics, licenses)
- Documentation presence/absence (binary, presence/absence)
- Security policy availability (binary, present/absent)
