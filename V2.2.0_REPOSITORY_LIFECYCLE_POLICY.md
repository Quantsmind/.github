## 1. Policy Overview

This policy defines the practical lifecycle stages for QuantsMind repositories on GitHub. It applies to all 46 repositories (4 public + 42 private) under the QuantsMind organization. The policy ensures consistent management from proposal through retirement, without arbitrary archival or deletion.

**Key Principle**: Practicality over bureaucracy. Every stage has objective criteria. No repository is archived or deleted without explicit review and documented justification.

---

## 2. Lifecycle Stages

### Stage 1: Proposal & Creation

**Purpose**: Establish a new repository with proper metadata and governance from inception.

**Criteria**:
- Clear project purpose and scope defined
- Ownership/maintainer assigned
- License selected (or "no license" explicitly declared)
- Project needs isolation that cannot be achieved in existing repos
- Review and approval by organization maintainers

**Required Setup**:
- Repository description (concise, accurate)
- 5–10 relevant GitHub topics (lowercase, hyphenated)
- `README.md` with getting-started guide
- `LICENSE` file or `LICENSE.md` (or `no-license` file explaining status)
- `CODE_OF_CONDUCT.md` (standard: [Contributor Convenant](https://www.contributor-covenant.org/))
- `CONTRIBUTING.md` with build/test/deploy instructions
- `README.md` badges: CI status, package version, license
- Branch protection rules on `main`
- Minimum CI workflow (lint, test)

**Exit Conditions** (promotion to Stage 2):
- All required metadata present
- Maintainer assigned and confirmed
- Initial commit pushed and CI passing

---

### Stage 2: Active Development

**Purpose**: Repository is under active feature development or bug-fixing.

**Criteria**:
- Regular commits (at least once per month during active periods)
- Open issues and pull requests being addressed
- CI pipeline passing on every push
- Version following semantic versioning (MAJOR.MINOR.PATCH) in README or package.json

**Maintenance Requirements**:
- Issues triaged within 30 days of creation
- Pull requests reviewed within 14 days
- Dependencies updated when security vulnerabilities disclosed
- CHANGELOG.md kept up to date for released versions

**Exit Conditions** (promotion to Stage 3 or archival):
- No commits for 6 consecutive months (maintenance stage)
- Project completed and ready for release readiness evaluation

---

### Stage 3: Maintenance

**Purpose**: Repository is stable, in security-fix-only mode, or in limited maintenance.

**Criteria**:
- No new features being developed
- Only critical security fixes applied
- Commits are infrequent (at most once per quarter)
- Issues are mostly closed or marked `wontfix`/`invalid`
- No pending pull requests

**Maintenance Requirements**:
- Security vulnerabilities addressed within 30 days
- Repository metadata kept current (description, topics)
- CI pipeline must still pass
- Open issues documented with status labels

**Exit Conditions** (promotion to Stage 4 or archival):
- No commits for 12 consecutive months → promotion to Stage 5 (archival)
- New active development begins → promotion to Stage 2

---

### Stage 4: Release Readiness

**Purpose**: Repository is stable and eligible for public release.

**Criteria**:
- All code committed to `main`; no work in progress
- CI pipeline passes on `main`
- All open issues either closed or marked with appropriate labels
- `CHANGELOG.md` covers all released versions
- `README.md` has installation/getting-started guide
- License is OSI-approved and clearly declared
- Security policy is in place (`.github/SECURITY.md`)
- Contributing guidelines are current
- At least one release tag exists (optional but recommended)

**Exit Conditions**:
- Repository promoted to public (WP2 review process)
- Archived (promotion to Stage 5)
- Development resumes (promotion back to Stage 2 or 3)

---

### Stage 5: Archival

**Purpose**: Repository is stable but no longer under active maintenance; moved to read-only status.

**Criteria**:
- No commits for 12 consecutive months
- Maintainer has confirmed archival intent
- No pending pull requests
- All open issues resolved or marked appropriate status

**Required Actions**:
- Set repository visibility to private (if previously public) or mark as archived
- Add archival notice to README: "This repository is archival. No further development or support is provided."
- Topics and description remain unchanged (historical record)
- Maintain read-only access for historical reference

**Exit Conditions**:
- New active development begins → unpause and promote to Stage 2
- Security issue requires fix → return to Stage 3

---

### Stage 6: Retirement

**Purpose**: Repository is being permanently removed from public view.

**Criteria**:
- Maintainer board decision confirmed via written record
- No valuable code or documentation to preserve
- Replacement repository exists or project is defunct
- Legal/ compliance requirements require removal

**Required Actions**:
- Create a final release tag with archival notice
- Mirror or export essential documentation to organization site
- Update README: "This repository has been retired. See [link] for replacement or migration path."
- Remove repository from active governance tracking
- Record retirement date and rationale in governance log

**Exit Conditions**: None. This is a terminal stage.

## 3. Transition Rules

| From → To | Conditions |
|-----------|------------|
| Stage 1 → 2 | All Stage 1 setup complete; maintainer confirmed |
| Stage 2 → 3 | No commits for 6 months; no pending PRs |
| Stage 3 → 4 | Release readiness criteria met |
| Stage 3 → 5 | No commits for 12 months; maintainer confirmation |
| Stage 4 → 2 | New active development detected |
| Stage 4 → 5 | Archived after release; promote to archival |
| Stage 5 → 2 | New development begins |
| Stage 5 → 6 | Board decision; legal/compliance requirement |
| Stage 6 → (terminal) | Permanent; no exit |

---

## 4. Review & Oversight

**Monthly Governance Check** (maintainer meeting, 15 minutes):
- Review all repos in Stages 2–4 for compliance
- Identify repos transitioning between stages
- Confirm maintainer availability and awareness
- Flag repos needing attention

**Quarterly Lifecycle Audit** (org maintainer review):
- Full inventory of all 46 repos and current stage
- Verify metadata completeness (description, topics)
- Check CI pipeline status for all repos
- Review archival/retirement candidates
- Update governance log

**Annual Policy Review** (organization-level):
- Policy revision based on organizational growth
- Criterion adjustments for new project types
- Lessons learned from archival/retirement cases
- Next year's review schedule confirmation

---

## 5. No Arbitrary Archival or Deletion

**Prohibited Actions**:
- ❌ Archive or delete any repository without following the full lifecycle review process
- ❌ Change repository visibility without documented justification and maintainer approval
- ❌ Rename repositories without backward-compatible reasoning
- ❌ Remove topics or descriptions without replacement metadata
- ❌ Disable CI or protection rules without replacement

**Required Documentation**:
- Every archival or retirement must be recorded in the governance log with:
  - Repository name and stage at transition
  - Date and rationale
  - Maintainer(s) who approved the action
  - Confirmation that no private data was lost without replacement

## 7. Appendices

### Appendix A: Stage Transition Triggers

**Automatic transition to Stage 3 (Maintenance)**:
- No commits detected in 6 consecutive months via GitHub Events

**Automatic transition to Stage 5 (Archival)**:
- No commits detected in 12 consecutive months AND maintainer confirmation

**Manual transition required**:
- Stage 2 → 3: Maintainer-initiated when development winds down
- Stage 3 → 4: Maintainer-initiated when release readiness criteria met
- Stage 4 → 5: Maintainer-initiated after release; archival review
- Stage 5 → 6: Organization maintainer board decision

### Appendix B: Minimum Metadata for Every Repository

Every QuantsMind repository must have:
1. Non-null description (even if "Internal organization repository" or "Project archive")
2. 3–10 relevant GitHub topics (lowercase, hyphenated; even if generic)
3. `README.md` with basic project overview
4. License declaration (OSI-approved license, "no license", or `MIT`/`Apache-2.0` as defaults)
5. `CODE_OF_CONDUCT.md` (Contributor Covenant standard)

### Appendix C: GitHub Actions for Lifecycle Management

| Action | When Triggered | Performed By |
|--------|---------------|--------------|
| Set topic recommendations | Stage 1 creation | Creator / maintainer |
| Enable branch protection | Stage 1 and above | Maintainer |
| Add security policy | Stage 4 release readiness | Maintainer |
| Mark archival notice | Stage 5 transition | Maintainer |
| Repository retirement | Stage 6 transition | Org maintainer board |
