## 1. Review Purpose

The governance review system ensures sustainable organizational maintainability through lightweight, repeatable procedures. It is designed for a small engineering organization and avoids bureaucracy while providing accountability and continuous improvement.

**Key Principles**:
- **Manageable**: Designed for small org; < 3 hours per quarter per maintainer
- **Evidence-based**: All decisions grounded in observable repository data
- **Actionable**: Reviews produce concrete action items, not just scores
- **Privacy-preserving**: No private repository details in public reports
- **Iterative**: Processes refine annually based on observed data

---

## 2. Review Cadence

| Review Type | Frequency | Duration | Participants | Output |
|-------------|-----------|----------|--------------|--------|
| **Quarterly Review** | Every 3 months | 2–3 days (spread over 6 weeks) | Org maintainers + assigned repo maintaines | Review checklist completed, action items identified, health scores updated |
| **Annual Governance Review** | Every 12 months | 3–5 days | All org maintainers | Policy refinements, health trend analysis, next year's schedule, governance log archival |

**Quarterly Review Schedule** (example, adjustable maintainer agreement):
- Q1: January–March → Review in April
- Q2: April–June → Review in July
- Q3: July–September → Review in October
- Q4: October–December → Review in January (also Annual)

**Annual Review Timing**: Conducted in January each year, covering the full calendar year.

## 3. Quarterly Review Checklist

### 3.1 Review Preparation (Week 1)

| Activity | Owner | Details |
|----------|-------|---------|
| Repo inventory confirmation | Org maintainer | Verify all 46 repos (4 public + 42 private) are accounted for; flag any new or removed repos |
| Maintainer assignment confirmation | Org maintainer | Confirm each repo has an assigned primary maintainer; flag unassigned repos |
| Tooling verification | Org maintainer | Ensure health framework dashboards, governance logs, and tracking spreadsheets are accessible |
| Previous action items review | Org maintainer | Check status of action items from previous quarter's review; carry forward unresolved items |

### 3.2 Per-Repository Assessment (Weeks 2–5)

Each repo is assessed across the V2.2.0 health framework indicators (from WP4). Assessment per repository:

| Indicator | Assessment Criteria | Evidence Collected |
|-----------|--------------------|-------------------|
| Description completeness | Non-null description; accuracy to project purpose | GitHub API `description` field screenshot or export |
| Topic coverage | 3–10 topics; relevance; standardization | GitHub API `repositoryTopics` names export |
| README quality | `README.md` presence; getting-started; docs link | `README.md` file review (root directory) |
| License presence | `LICENSE`/`LICENSE.md` present; SPDX identifier | File listing + SPDX identifier check |
| Contribution guidance | `CONTRIBUTING.md` present; `CODE_OF_CONDUCT.md` present | File existence check |
| Issue maintenance | All open issues labeled; no issues >6 months unlabeled | GitHub API issue query: `search Issues` by repo |
| Release documentation | Release tags present; `CHANGELOG.md` existence | GitHub API release query; `CHANGELOG.md` file check |
| Security policy | `.github/SECURITY.md` present; actionable content | File existence + content review |

**Assessment Output Per Repository**:
- Health score (0–100%, percentage of 8 indicators fully met)
- Pass/fail per indicator (✅ / ⚠️ / ❌)
- Specific action items for each ❌ or ⚠️ indicator
- Maintainer notes on context or exceptions

### 3.3 Review Compilation (Week 6)

| Activity | Owner | Output |
|----------|-------|--------|
| Aggregate health scores | Org maintainer | Organization average health score; distribution chart |
| Identify regressions | Org maintainer | Any indicator declining >10 percentage points QoQ |
| Track action item resolution | Org maintainer | Status of all carry-forward items from prior quarter |
| Identify improvements | Org maintainer | Any indicator improving >10 percentage points QoQ |
| Flag exceptions | Org maintainer | Repos with unusual circumstances requiring special handling |

**Compilation Output**:
- Organization health dashboard (current quarter vs. prior quarter)
- Action item tracking table (opened, closed, carried forward)
- Exception log (repos with special circumstances)
- Priority list for next quarter's focus

## 4. Annual Governance Review Procedure

### 4.1 Annual Review Scope

The annual review covers the full calendar year and includes:

| Component | Description |
|-----------|-------------|
| **Health Score Trend** | Compare 4 quarterly health scores against prior year's annual average |
| **Policy Effectiveness** | Evaluate whether V2.2.0 lifecycle policy (WP1) and promotion policy (WP2) are achieving their intended goals |
| **Metric Refinement** | Review each of the 8 health indicators; adjust criteria based on observed data and organizational growth |
| **New Indicator Consideration** | Evaluate if any new evidence-based indicators should be added (e.g., CI pipeline success rate, dependency update frequency) |
| **Privacy Boundary Review** | Confirm no private information has leaked into public health reports; re-affirm boundary enforcement |
| **Maintainer Workload Assessment** | Review maintainer time commitment; adjust quarterly review scope if over/under capacity |
| **Next Year's Schedule** | Confirm quarterly review dates and maintainer assignments for coming year |
| **Governance Log Archival** | Archive the year's governance logs; ensure searchable storage for future reference |

### 4.2 Annual Review Output

| Document | Description |
|----------|-------------|
| `V2.x.0_Governance_Annual_Review.md` | Full annual review report |
| `V2.x.0_Metric_Refinements.md` | Any revised indicator definitions or new indicators added |
| `V2.x.0_Maintainer_Calendar.md` | Updated maintainer assignment calendar for coming year |
| `V2.x.0_Governance_Log_Archive.md` | Curated archive of the year's governance data |

### 4.3 Annual Review Ownership

| Role | Responsibility |
|------|----------------|
| **Org maintainer lead** | Facilitates the review; ensures all maintainers complete their assessments; compiles the annual report |
| **Individual maintainers** | Complete per-repository assessments for assigned repos; submit action items; participate in discussion |
| **All maintainers** | Participate in policy effectiveness discussion; vote on refinements (simple majority) |

### 4.4 Annual Review Timeline

| Phase | Timing | Activity |
|-------|--------|----------|
| **Preparation** | First 2 weeks of January | Distribute review checklists; confirm maintainer assignments; verify tooling |
| **Assessment** | Weeks 3–8 of January | Maintainers complete per-repository assessments; submit to org maintainer lead |
| **Compilation** | Weeks 9–10 of January | Org maintainer lead aggregates data; identifies trends and refinements |
| **Discussion** | Week 11 of January | All maintainers discuss findings; vote on policy refinements |
| **Finalization** | Last week of January | Finalize annual report; publish calendars; archive governance logs; plan Q1 reviews |

**Duration**: 11 weeks (approximately 2.5 months)  
**Commitment**: ~10 hours per maintainer over the full annual cycle (spread across quarters)

## 5. Review Checklist (Quarterly — Per Repository)

| # | Indicator | Status | Evidence | Action Item | Owner | Due |
|---|-----------|--------|----------|-------------|-------|-----|
| 1 | Description completeness | ✅ / ⚠️ / ❌ | GitHub API `description` | If ❌: add description; if ⚠️: review accuracy | Maintainer | Next review |
| 2 | Topic coverage | ✅ / ⚠️ / ❌ | GitHub API `repositoryTopics` | If ❌: add topics; if ⚠️: review relevance | Maintainer | Next review |
| 3 | README quality | ✅ / ⚠️ / ❌ | `README.md` review | If ❌: create README; if ⚠️: improve content | Maintainer | Next review |
| 4 | License presence | ✅ / ⚠️ / ❌ | `LICENSE`/`LICENSE.md` file | If ❌: add license file | Maintainer | Next review |
| 5 | Contribution guidance | ✅ / ⚠️ / ❌ | `CONTRIBUTING.md` + `CODE_OF_CONDUCT.md` | If ❌: create both files | Maintainer | Next review |
| 6 | Issue maintenance | ✅ / ⚠️ / ❌ | GitHub issue query results | If ❌: label/triage issues | Maintainer | Next review |
| 7 | Release documentation | ✅ / ⚠️ / ❌ | Release tags + `CHANGELOG.md` | If ❌: create release + changelog | Maintainer | Next review |
| 8 | Security policy | ✅ / ⚠️ / ❌ | `.github/SECURITY.md` | If ❌: create security policy | Maintainer | Next review |

**Per-Repository Total**: Count of ✅, ⚠️, ❌ indicators; calculate health score = (✅ count / 8) × 100

## 6. Exception Handling

### 6.1 Types of Exceptions

| Exception Type | Description | Handling |
|----------------|-------------|----------|
| **Missing data** | Indicator cannot be assessed (e.g., private repo, no CI) | Mark as "N/A — data unavailable"; exclude from health score calculation for that repo; note for future quarter when data may be available |
| **Conflict of interest** | Maintainer assigned to their own repo has biased assessment | Recuse; another maintainer completes the assessment; document recusal |
| **Resource constraint** | Maintainer unable to complete assessment within quarter | Document as "carry forward"; prioritize critical indicators (description, license, security); partial assessment still valuable |
| **Policy ambiguity** | Indicator criteria unclear or ambiguous | Escalate to org maintainer team; interim guidance provided; refine criteria in next annual review |
| **Privacy concern** | Assessment would reveal private information | Mark as "privacybound"; exclude from public reporting; handle privately per organization policy |

### 6.2 Exception Workflow

1. Maintainer identifies exception during assessment
2. Maintainer documents exception type and rationale in assessment tool
3. Org maintainer reviews exception within 5 business days
4. Org maintainer assigns resolution:
   - If "Proceed with modification": adjust criteria temporarily; complete assessment
   - If "Mark N/A": record in governance log; exclude from scoring
   - If "Postpone": set deadline; reassess next quarter
5. Resolution documented in governance log

## 7. Action Tracking

### 7.1 Action Item Lifecycle

| Stage | Description | Owner | Timeframe |
|-------|-------------|-------|-----------|
| **Identified** | Action item created during review | Maintainer | — |
| **Assigned** | Action item assigned owner; due date set | Org maintainer | Within 5 business days |
| **In Progress** | Work initiated on action item | Assigned owner | — |
| **Completed** | Action item fully resolved | Assigned owner | — |
| **Verified** | Org maintainer confirms resolution | Org maintainer | Within 5 business days of completion |
| **Closed** | Action item logged as resolved; no further work needed | Org maintainer | After verification |

### 7.2 Action Item Tracking Table

### 7.3 Carry-Forward Policy

- Unresolved action items from one quarter **automatically carry forward** to the next quarter's review
- Org maintainer reviews carry-forward items at the start of each quarter
- Items carried forward for >4 quarters are escalated to org maintainer team for prioritization or deprioritization
- No more than 20 total carry-forward items at any time; if threshold exceeded, prioritization review called

## 8. Completion Criteria

### 8.1 Quarterly Review Completion

A quarterly review is considered complete when:

| Criterion | Requirement |
|-----------|-------------|
| **Inventory** | All 46 repos accounted for in assessment |
| **Coverage** | ≥ 90% of assigned repos have complete health assessments (✅/⚠️/❌ for all 8 indicators) |
| **Action Items** | All identified action items are assigned, tracked, and have due dates |
| **Health Scores** | Organization average health score calculated and recorded |
| **Exceptions** | All exceptions documented with rationale in governance log |

If any criterion is not met, the org maintainer team decides whether to:
- Extend the review period by 2 weeks
- Escalate to all maintainers for collective completion
- Carry forward with documented justification

### 8.2 Annual Review Completion

An annual review is considered complete when:

| Criterion | Requirement |
|-----------|-------------|
| **Full Inventory** | All 46 repos assessed across all 4 quarters |
| **Health Trend** | Annual average health score calculated and compared to prior year |
| **Policy Evaluation** | Policy effectiveness discussion completed; refinements voted on |
| **Maintainer Calendar** | Next year's quarterly calendar confirmed and published |
| **Governance Log** | Year's governance data archived and searchable |
| **Action Item Resolution** | ≥ 70% of carry-forward items from prior year resolved or actively in progress |

If any criterion is not met, the org maintainer team decides whether to:
- Extend the annual review period by 2 weeks
- Defer certain components to Q1 of coming year
- Convene a special maintainer meeting to address gaps

## 9. Governance Log

### 9.1 Logging Requirements

Every review action must be recorded in the organization governance log with:

| Field | Description |
|-------|-------------|
| **Timestamp** | ISO date-time when action occurred |
| **Review Type** | "quarterly" or "annual" |
| **Component** | "health-assessment", "action-tracking", "policy-refinement", "exception-handling" |
| **Repository** | Repo name (or "org-wide" for organization-level actions) |
| **Actor** | Maintainer or org maintainer who performed the action |
| **Action** | Description of what was done |
| **Result** | Outcome (completed, carried forward, N/A, etc.) |
| **Evidence Link** | Link to supporting data (API export, file snapshot, etc.) |

### 9.2 Governance Log Storage

- **Location**: `.github/governance/log/` directory
- **Format**: Markdown files, one per review session
- **Naming Convention**: `YYYY-MM-DD_<quarterly|annual>_<component>.md`
- **Example**: `2026-11-01_quarterly_health-assessment.md`

### 9.3 Governance Log Retention

- Minimum 3-year retention
- Annual archive published to `.github/governance/archive/`
- Searchable by repository, indicator, or date

## 10. No External Reminders or Automations Without Authorization

**Prohibited** without explicit org maintainer board authorization:

| Prohibited Action | Reason |
|-------------------|--------|
| Recurring calendar events for quarterly reviews scheduled >1 year in advance | Reduces flexibility; maintainers may rotate or leave |
| Automated email reminders for action item due dates | Creates noise; maintainers manage their own commitments |
| Automated health score calculations via GitHub Actions | Creates single point of failure; manual evidence-based assessment preferred |
| External service integrations (Slack, Jira, etc.) for review notifications | Increases organizational attack surface; not all maintainers use these services |

**Allowed**:
- Manual calendar invitations sent by org maintainer at review start
- Maintainers' personal task management for action item due dates
- Spreadsheet-based tracking (offline, maintainer-controlled)
- Annual review schedule confirmed at year-start (adjustable with maintainer consensus)
