## 1. Policy Overview

This policy defines the review process for promoting private repositories to public repositories within the QuantsMind organization. No repository is promoted automatically. Every promotion requires explicit review and approval following the criteria below.

**Key Principle**: No repository is promoted without thorough review. Intellectual property, security, and privacy boundaries must be respected. The public/private boundary is strictly enforced.

---

## 2. Promotion Review Process

### Phase 1: Initial Assessment (Maintainer-Led)

The repository's owning maintainer initiates the promotion request. The assessment covers:

| Criterion | Requirement | Evidence Needed |
|-----------|-------------|-----------------|
| **Intellectual Property** | All code is original or properly licensed | License verification; third-party code attribution records |
| **Licensing** | Repository uses an OSI-approved license or `no license` is declared | `LICENSE` file or `LICENSE.md` content; SPDX identifier present |
| **Security** | No secrets, tokens, or credentials in code | `git -C <path> grep -r --include='*.py' --include='*.js' --include='*.ts' -E '(?i)(api[_-]?key|auth[_-]?token|secret|password)'` run; `git -C <path> grep -r --include='*.tf' -E '(?i)(secret|token|password)'` |
| **Dependency Review** | All dependencies have compatible licenses | `pip-licenses` or `npm audit` report; license compatibility matrix |
| **Documentation** | `README.md` describes project purpose clearly | README content reviewed for completeness |
| **Private Infrastructure** | No references to internal systems, endpoints, or infrastructure | Search for internal hostnames, IP ranges, network references |
| **Sensitive Information** | No confidential project details, roadmaps, or metrics | Content review of README, docs, comments |
| **Release Readiness** | Stable code on `main`; CI passing | CI pipeline status; at least one release tag |

**Pass Threshold**: All 7 criteria must pass. If any criterion fails, the maintainer must resolve the issue before promotion can be considered.

---

### Phase 2: Organizational Review (Org Maintainer-Led)

If the initial assessment passes, the request moves to organizational review. The org maintainer team reviews:

| Criterion | Reviewer | Decision |
|-----------|----------|----------|
| **IP & Licensing** | All maintainers | Approve / Reject |
| **Security** | Security-conscious maintainer | Approve / Reject |
| **Public Readiness** | Maintainers with repo expertise | Approve / Reject |
| **Brand/Organization Impact** | Org maintainer lead | Approve / Reject |
| **Final Decision** | Simple majority of maintainers | Promote / Not Promote |

**Recusal**: Any maintainer with a conflict of interest (e.g., originally authored sensitive code) must recuse from the vote.

**Timeline**: Phase 1 must complete within 14 days of request. Phase 2 must complete within 30 days of Phase 1 passing.

---

### Phase 3: Promotion Execution

If the organizational review approves, the following actions are taken:

1. **Fork creation** (if needed): Create a public fork or new repository under the QuantsMind organization
2. **Metadata cleanup**:
   - Ensure description is public-friendly (no internal references)
   - Set 5–10 relevant GitHub topics (lowercase, hyphenated)
   - Verify `README.md` has getting-started guide, installation instructions, contribution guide
   - Verify `LICENSE` file is present and correct
   - Verify `CODE_OF_CONDUCT.md` is present
   - Remove or obfuscate any private infrastructure references
3. **Security policy**: Ensure `.github/SECURITY.md` is present (create if missing for public repos)
4. **Topic configuration**: Apply standardized topic set per project category
5. **Visibility change**: Set repository visibility to `public`
6. **Announcement**: Update organization profile README if the repo is a featured project
7. **Label taxonomy**: Adopt the standardized issue label set (9 preserved + 11 optional new labels)

**Post-Promotion Monitoring**: For 90 days after promotion, the owning maintainer should:
- Monitor issue reports for previously-undisclosed sensitive content
- Respond to pull requests within 14 days
- Triage issues within 30 days
- Report any security concerns to the org maintainer team immediately

---

## 3. Promotion Prohibitions

The following actions are **strictly prohibited** without explicit org maintainer board approval:

| Prohibited Action | Reason |
|-------------------|--------|
| Automatic promotion based on labels or metadata alone | Each repo requires individual review |
| Promotion without IP/licensing verification | Legal risk to organization |
| Promotion of repos with undetected secrets | Security risk to organization and users |
| Promotion without maintaining private/private boundary | Organizational policy violation |
| Promoting repos with confidential roadmaps or metrics | Competitive and privacy risk |
| Bypassing the org maintainer review vote | Governance bypass |

---

## 4. De-Promotion (Public → Private)

A public repository may be de-promoted to private if:

| Criterion | Required Action |
|-----------|-----------------|
| Confidential information discovered post-promotion | Immediate de-promotion; investigate and remediate |
| Security breach or secret leakage | Immediate de-promotion; rotate credentials |
| Maintainer requests de-promotion | Review per Phase 1 criteria; may return to private |
| Repository no longer meets public readiness criteria | Follow archival/lifecycle policy (WP1 Stage 5/6) |

**De-Promotion Process**:
1. Org maintainer team reviews the case
2. If approved, set visibility to `private`
3. Add de-promotion notice to README: "This repository was promoted to public on [date] but is now de-promoted to private. See internal policy for details."
4. Remove public topics; replace with internal classification topics if warranted
5. Record de-promotion date and rationale in governance log
6. Notify affected maintainers

## 5. Topic Standards for Promoted Repositories

Upon promotion, each repository receives a standardized topic set based on its primary category:

| Category | Topics (5–10 total) |
|----------|---------------------|
| **Quantum Computing** | `quantum`, `quantum-computing`, `quantum-simulation`, `quantum-benchmarks` |
| **SDK / Library** | `sdk`, `library`, `development`, `api` |
| **Artificial Intelligence** | `ai`, `machine-learning`, `data-science`, `ai-reasoning` |
| **Systems / Programming** | `compiler`, `programming-language`, `systems`, `go`, `rust` |
| **Security** | `security`, `threat-intel`, `supply-chain`, `sbom` |
| **General** | `opensource`, `python`, `typescript`, `go`, `rust` |

**Topic Assignment Rules**:
- Minimum 5, maximum 10 topics per repository
- Topics must be relevant to the project's actual capabilities
- No duplicate topics across repos in the same category
- Topics are lowercase, hyphenated as needed
- Topics are assigned during Phase 3: Promotion Execution

---

## 6. Promotion Record

Every promotion must be recorded in the organization governance log with:

| Field | Description |
|-------|-------------|
| **Repository name** | Full repo name (e.g., `QuantsMind-SDK`) |
| **Promotion date** | ISO date (e.g., `2026-11-06`) |
| **Promoted by** | Maintainer or org maintainer who approved |
| **Review phase outcomes** | Pass/fail per each criterion |
| **Topic set applied** | List of GitHub topics assigned |
| **License declared** | SPDX identifier |
| **Security policy status** | Present/absent |
| **Post-promotion monitoring end date** | 90 days from promotion |

## 5. Appendix: Security Scanning Checklist

| Check | Command/Method | Pass Criteria |
|-------|---------------|---------------|
| Secret scanning (general) | `git -C <repo> grep -r -i -E '(api_key|api-token|secret|password').' -- '(*.py|*.js|*.ts|*.go|*.yaml|*.yml|*.json|*.env)'` | No matches, or all matches are documented test fixtures |
| Token scanning | `git -C <repo> grep -r -i -E '(?i)token[^\\s]{10,}'` | No matches beyond legitimate variable names |
| Dependency license check | `pip-licenses --format=spdx` or `npm audit --json` | All dependencies have compatible licenses; no prohibited licenses |
| Private infrastructure reference | Search for internal hostnames, IP ranges (10.x, 192.168.x, 172.16-31.x), internal endpoint patterns | No matches, or all matches are documented as public endpoints |
